## Verdict in one paragraph

The six-context map is fundamentally sound and unusually well-evidenced: the
Execution/Catalog split is confirmed by the KB's own criteria (different
lifecycles, invariants, consistency needs, and language ⇒ different models in
different contexts), RCP is a textbook Published Language, and the iOS
RecipeSnapshot matches the "Bounded Contexts should store all the data they
need locally" rule. The serious gap is not the map — it is **where runtime
behavior lives**. The design says "apps never validate; they consume
already-validated documents with generated decode types", yet the same design
requires the scaler and substitution engine to *refuse* to violate critical
safety constraints, resolve guard paths, and re-estimate durations — at
runtime, on-device, offline. That behavior must be implemented somewhere in
TS, Swift, and Go, and nothing in the model names or owns it. Left unnamed,
it will be hand-written three times — the exact drift class this whole effort
exists to eliminate — and the generated decode types will quietly become an
Anemic Domain Model in every app. Secondary gaps: the mutable draft/authoring
lifecycle is unmodelled, several lifecycle events are missing, and the derived-
facet indexer has no owning context.

## Findings

| # | Area | Severity | Detail (with KB citations) |
|---|---|---|---|
| F1 | Behavior placement / anemic model | **critical** | "Apps never validate" (DECISIONS #8) coexists with runtime obligations: scaling with `min_batch`/`maintenance` exceptions, guard-path selection, checkpoint re-estimation of `until` durations, and safety-constraint refusal ("neither the scaler nor the substitution engine may produce a document that violates a `critical` constraint" — D7). This is domain behavior, not decoding. quicktype-generated Codable/TS types are getters-only by construction — Vernon warns: "all of your Aggregates have only public accessors... Designing an Anemic Domain Model requires you to take on all the overhead of a domain model without realizing any of its benefits" (*DDD Distilled* ch. 5); *DDD in PHP* ch. 12 flags data-first modeling as the anemic trap. No context in section D owns this "Recipe Calculus". Unowned, it gets reimplemented per stack — recreating the drift the schema was built to kill. Mitigation exists in the KB: Vernon's FP nuance — immutable records + pure functions over them is a legitimate non-anemic style — but the functions must be a *named, conformance-tested* part of the model. |
| F2 | Missing domain events — lifecycle ends | warning | The event list covers happy paths only. Missing: `RecipeDeprecated`/`RecipeSuperseded` (immutable-once-published means errata arrive as new versions — what signals that v2 supersedes v1 to Execution snapshots and Planning?), `DraftRejected` (verification workflow has promotion but no refusal path), `SessionAbandoned` (append-only sessions that never complete need a terminal event or they leak). KB: "Model information about activity in the domain as a series of discrete events... when something happens that domain experts care about, capture it as a Domain Event"; "Use Domain Events as the starting point for modeling business processes" (Domain Event synthesis). A heritage archive *especially* cares about supersession — provenance is first-class (D10). |
| F3 | Missing domain event — variant drift | warning | DECISIONS #9 ships variants + op-lists from day one, with the acknowledged drift risk ("a base-recipe edit must propagate to N variants", mitigated by a "CI diff-alarm"). That alarm is a domain occurrence with a downstream reaction (re-review), not a CI detail: `VariantDriftDetected` (or `BaseRecipeChanged` consumed by a variant-review policy) belongs in the event list. KB: "Model time expiration as a Domain Event, and not as a command, if the business cares about this fact"; cross-aggregate reactions go through events + eventual consistency ("Update other Aggregates using eventual consistency" — Vernon's rule 4). |
| F4 | Unowned projection — derived facets | warning | Facets are "derived at index time, never stored in the document" (deep-dives §C), and derivation needs *both* Catalog content and Registry data (allergens = ingredient classes × EU-FIC). No context owns the indexer. KB: bounded contexts are defined by capability — "Focus on business capabilities rather than data when defining bounded contexts"; a projection that reads two contexts' models must itself live somewhere with an explicit dependency direction, or it becomes shared-database integration by stealth ("Avoid shared database integration" — Bounded Context synthesis). Likely home: Publishing/Heritage (it already owns packs/curation projections), consuming `RecipePublished` + Registry data. |
| F5 | Shared kernel across stacks — semantic linter | warning | Layer-2 validation is "a small library (TS first)" run "in CI on YAML sources and at API write time" (deep-dives §A) — but the API is Go. Either the Go API shells out to node, or the linter is reimplemented: an accidental Shared Kernel across a language boundary. KB: "Code reuse between BOUNDED CONTEXTS is a hazard to be avoided" (trap); a Shared Kernel is "often very difficult to conceive... and difficult to maintain" (*DDD Distilled* ch. 4). Same root cause as F1 — decide once where shared executable semantics live and how conformance is proven (test vectors in the published language work across stacks; shared source does not). |
| F6 | Unmodelled aggregate state — the draft | warning | "Recipe: versioned, immutable once published" defines the *end* state; the mutable authoring state is unmodelled. Is a draft a Recipe in `status: draft`, or its own aggregate (as Ingestion's ImportDraft suggests)? Who may edit, what invariants hold pre-publish, what does `RecipePublished` actually transition? KB: aggregates are designed around what "must be consistent when a transaction is committed" (Vernon rule 1) — the draft is the only Recipe state with concurrent-edit transactions at all, so it is the state that most needs aggregate rules. Note the happy consequence: because published recipes are immutable, the "design small Aggregates" concurrency pressure (*DDD in PHP* ch. 12: smaller boundary ⇒ fewer commit conflicts) applies only to drafts — a large Recipe aggregate is fine *once published*, and this should be said explicitly. |
| F7 | Ubiquitous language — gaps and collisions | warning | (a) `CookingSession` vs today's `BakeSession` — pick the term and rename the code or the doc ("The code must be based on the ubiquitous language"). (b) `Measurement` appears in Execution ("Timer, Measurement") while the recipe holds measurement *targets* — same word, two contexts, two meanings; legal per "Ubiquitous Language is only Ubiquitous within a given Bounded Context", but the doc should say so explicitly ("Disagreements in language between contexts should be made visible"). (c) PT/EN mix: Fornada, massa-mãe (Planning) vs Recipe, Session (elsewhere) — fine *across* contexts, but each context should commit to one language internally. (d) Undefined load-bearing terms: variant vs fork vs `lineage.family`; option vs guard vs path; draft vs unverified. KB: "Missing terms in design are opportunities for improvement"; "The Ubiquitous Language must be rigorous." A per-context glossary is the cheap fix. |
| F8 | Context relationship mislabelled — RecipeSnapshot | info | RecipeSnapshot (copy-on-reference, `payloadJSON`) is called an ACL, but an ACL *translates* an upstream model into the downstream's own. If iOS decodes RCP as-is, the relationship is Conformist-to-Published-Language + local copy — which the KB rates as the *best* integration experience ("Often an Open Host Service serves and consumes a Published Language, which provides the best integration experience"; "Keep a local copy of data within a Bounded Context because storage is cheap"). If iOS translates payloadJSON into its own ExecutionStep model (it does), then the ACL label is right for that layer. Worth one precise sentence: snapshot = local copy; the Swift mapping = the ACL. |
| F9 | Registry: context vs module (open decision) | info | KB gives the decision rule directly: "Prefer Modules over Bounded Contexts when terminology is fuzzy" and "Segregate Supporting Subdomains within a Bounded Context using Modules." Registry terminology is *not* fuzzy and its cadence/governance differ — but it has one team and one repo today. Recommended shape: separate *documents and schemas* now (they are published-language artifacts either way), Registry as a module of Catalog organizationally, promoted to a full context when contributor governance (B6) makes it a separate team concern ("Assign one team to work on one Bounded Context"). |
| F10 | Three contexts labelled "core" | info | Catalog (core), Execution (core), Publishing/Heritage ("core for the site"). Core-domain distillation is per product effort, so this is defensible — but it should be stated as such, or every context gets core-level investment ("Bounded Context should hold closely all concepts that are core to the strategic initiative and push out all others"). Suggested framing: site → Publishing/Heritage core; app → Execution core; the RCP effort itself → Catalog core; Registry, Planning, Ingestion supporting everywhere. |
| F11 | Boundary confirmations (no action) | info | Positive findings, cited for the record: (a) Execution as separate context satisfies "Two distinct purposes should map to two different models, inside different bounded contexts" and does **not** trip the "Avoid dissecting an aggregate into two different bounded contexts" trap — targets-in-recipe / readings-in-session are two models of measurement, not one aggregate split. (b) Component references by `id + version` follow "Reference other Aggregates by identity only" / "reference them by ID rather than embedding". (c) Cross-context updates (SessionCompleted → Planning calibration) follow "Update other Aggregates using eventual consistency" and "Domain Event consumers should depend only on the event schema (Published Language), not the event types of the publisher" — which also confirms Planning must consume the event *schema*, never the iOS LocalEvent internals. (d) Event names are past-tense per the naming rule. (e) The append-only session with LocalEvent log matches "Event sourcing enables expressive behavior-focused aggregates." |

## Recommendations

| Priority | Action | Rationale |
|---|---|---|
| P1 | Name the runtime behavior model — a **"Recipe Calculus"** (scaling, basis resolution, guard-path selection, safety-constraint enforcement, duration re-estimation) — as an explicit part of the Catalog context's published contract: specify it as pure functions over the immutable RCP document, and ship **conformance test vectors in the published language** (input doc + operation + expected output/refusal) that all three stacks must pass. | Resolves F1 and F5 with one mechanism. Vernon's FP nuance makes immutable-data + pure-functions non-anemic *if the functions are part of the model*; test vectors give cross-stack conformance without a shared-kernel source dependency ("Code reuse between BOUNDED CONTEXTS is a hazard"). This is the highest-leverage fix: it converts "apps never validate" into the precise, true statement "apps never *admit* documents; they *compute* over admitted documents with a conformance-tested calculus." |
| P2 | Model the Recipe lifecycle state machine explicitly: Draft → Published → Superseded/Deprecated, with the draft's edit invariants stated, and add the missing events `RecipeSuperseded` (or `RecipeDeprecated`), `DraftRejected`, `SessionAbandoned`. | F2, F6. The draft is the only concurrently-mutable Recipe state, so it is where aggregate rules earn their keep; supersession is a first-class heritage concern (provenance, D10) and downstream snapshots need the signal. |
| P3 | Add `VariantDriftDetected` (base changed; N variants unreviewed) to the event list and treat the CI diff-alarm as its publisher; Publishing's review workflow is the consumer. | F3. Decision #9's known drift risk gets a domain-level home instead of living as tooling folklore; matches "capture what domain experts care about as a Domain Event." |
| P4 | Assign the derived-facet indexer to Publishing/Heritage as a projection consuming `RecipePublished` + Registry catalogs; document the dependency direction (Publishing ← Catalog, Publishing ← Registry). | F4. Projections need an owner or they become shared-database integration by stealth; Publishing already owns the sibling concern (packs/curation projections). |
| P5 | Write the per-context glossary: rename `BakeSession` → `CookingSession` (or keep BakeSession and say why), define variant/fork/family, option/guard/path, draft/unverified, and mark the deliberate `Measurement`(target) vs `Reading` split as a cross-context language boundary. | F7. Cheap, and per the KB the act of writing it surfaces model gaps ("Missing terms in design are opportunities for improvement"). |
| P6 | Keep Registry as separate schemas/documents now but a module organizationally; add "promote to full context" as an explicit trigger tied to the contributor-governance milestone (B6). Clarify the RecipeSnapshot sentence (snapshot = local copy; Swift mapping = ACL). State core-domain distillation per product. | F8, F9, F10. Closes three open threads with decisions the KB supports directly, at zero implementation cost. |

**KB passages retrieved (Step 3, `search_bok`):**

- *DDD Distilled* ch. 4 — Anticorruption Layer, Open Host Service, Published Language, Shared Kernel, Conformist.
- *Domain-Driven Design* (Evans) ch. 6 — aggregate boundary/reference rules; ch. 14 — Published Language: "do not equate the interchange language and the model of the host."
- *Strategic Monoliths and Microservices* — Context Mapping pattern catalogue (Published Language as schemas for documents, commands, events).
- *DDD in PHP* ch. 12 — small vs big aggregates (transactional contention); Anemic vs Rich Domain Models.
- *Domain Storytelling* ch. 12 — anemic = data-centric model that lets rules be broken.

**Heuristics (Step 3, `search_heuristics` + synthesis-linked):** protect business invariants inside aggregate boundaries; design small aggregates; reference other aggregates by identity only; update other aggregates using eventual consistency; avoid dissecting an aggregate into two bounded contexts (trap); code reuse between bounded contexts is a hazard (trap); prefer Modules over Bounded Contexts when terminology is fuzzy; two distinct purposes map to two models in different contexts; domain-event consumers depend only on the event schema; name events in past tense per the UL; missing terms in design are opportunities; keep a local copy of data — storage is cheap; event sourcing enables behavior-focused aggregates; avoid the Anemic Domain Model (smell).
